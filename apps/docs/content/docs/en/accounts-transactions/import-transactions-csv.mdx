---

CSV import brings a bank statement into an account when a bank connection is not available, or adds history from before the connection started.

## Before you start

Any bank's statement export works, as CSV (any delimiter), Excel (`.xls`, `.xlsx`), OFX/QFX (`.ofx`, `.qfx`), QIF (`.qif`) or CAMT.053 (`.xml`). Download it from your bank's website and leave it as the bank wrote it: rows above the column names and totals below the transactions are fine.

OFX and QFX are the formats most banks and Quicken offer as a download. WonderMoney reads both OFX 1.x (SGML) and OFX 2.x (XML), and decodes the file by the encoding it declares, so accented payee names stay intact even when the bank wrote Windows-1252 or ISO-8859-1. Each transaction's bank id (`FITID`) is what marks it as already imported, so re-importing the same file adds nothing. A transaction with no id, or with an id another row of the same account repeats, falls back to its date and amount. A file with several accounts asks which of your accounts each one goes to. Investment statements (`INVSTMTRS`) and statements that hold only a balance are skipped, with a note in the import.

QIF is the format Quicken, Microsoft Money and GnuCash export. WonderMoney reads bank, credit-card, cash and other QIF files, and keeps each record's sign: money out is negative, money in positive. A record with split lines imports as one transaction with the record's own total; the breakdown goes into the transaction's description. QIF has no transaction id, so a re-import of the same file finds each row by its date and amount. QIF dates have no standard format either: WonderMoney reads every date in the file to tell day first from month first, and when the file cannot say (every day and month is 12 or less) it asks you to choose before importing. A category in the file (`L`) is kept with the row, and a transfer to another account (`L[Account]`) imports as a transfer. A file with several accounts (`!Account` blocks) asks which of your accounts each one goes to. Investment records (`!Type:Invst`) are skipped, with a note in the import.

CAMT.053 is the ISO 20022 end-of-day statement that SEPA banks are replacing MT940 with, and the most reliable file a European bank offers. WonderMoney reads the statements of a `BkToCstmrStmt` document: each entry's booking date (`BookgDt`, or its value date when the bank writes no booking date) is the transaction date, and `CdtDbtInd` decides the direction, so a debit is negative and a credit positive. The counterparty name and the remittance information become the merchant and the description. An entry's `AcctSvcrRef`, then its `NtryRef`, is what marks it as already imported; an entry with neither, or with a reference another entry of the same account repeats, falls back to its date and amount. A batch booking that holds several transactions imports as one row per transaction when they add up to the entry's amount, and as the single entry otherwise. Entries the bank has not booked yet (`Sts` other than `BOOK`) are skipped, with a note in the import. Each statement is labelled by its IBAN, and a file with several asks which of your accounts each one goes to, pre-filled when one of your accounts holds that IBAN as its account number. A file that declares a document type (`DOCTYPE`) is refused: a bank statement never has one, and it is how an XML file tries to read data it should not.

For Millennium BCP, ActivoBank, Bankinter, Banco BPI and Montepio, WonderMoney reads the bank's own format when the account has that bank as its financial institution. For every other file, it finds the date, description and amount columns from their names, and works out the date format and the decimal separator from the values. When the names don't settle it, an AI model is asked which column is which: it sees the column names and what kind of values each column holds (dates, numbers, text), never your descriptions, amounts or dates. That uses one of your household's daily CSV mapping calls; on an instance without AI, or once the day's calls are used, you pick the columns yourself.

A file in the older WonderMoney CSV template (with `internalTransactionId` and `transactionTypeKey` columns) goes through the same review; its type column decides whether each row is money in or money out.

On a self-hosted instance, imports also need [file storage](/en/docs/self-hosting/configure#file-storage).

## Steps

1. Download the statement from your bank as CSV, Excel, OFX, QFX, QIF or CAMT.053 XML.
2. Open the account and choose **Import transactions**.
3. Add the file (up to 5 MB). WonderMoney reads it straight away and shows how many transactions it found, the dates they cover, and the first few rows. An OFX/QFX, QIF or CAMT.053 file has no columns to preview: it goes straight to the review.
4. Check the rows. If a column is wrong, open **Adjust columns** and pick the right one, or change the date format, the number format, or whether spending is shown as a positive amount (as on some credit card statements). The preview updates as you change them.
5. Choose **Review transactions**. WonderMoney reads every row of the file and lists them, with nothing imported yet:
   - **New**: not in the account yet. These are included.
   - **Already in the account**: the same transaction was imported before, from this file or an overlapping export. These are skipped.
   - **Possible duplicate**: nothing in the file identifies it as a transaction already in the account, but the account holds one with the same amount within a few days. These are skipped unless you include them. See [Possible duplicates](#possible-duplicates).
   - **Couldn't be read**: a row whose date or amount could not be read, with the reason. These never import.
6. Check the list. Untick a row to skip it, or tick one to include it. Show one kind of row and choose **Include all** or **Skip all** to decide them together.
7. Choose **Import**, which shows how many transactions it will add. The import runs in the background and shows its progress. If it stops part way (for example, the server restarts), choose **Try again**: it carries on from where it stopped, and nothing is imported twice.

A file that holds several accounts asks which of your accounts each one goes to before it can be imported. In an OFX/QFX file each account is labelled by the bank's own account id (`ACCTID`); in a QIF file, by its `!Account` name; in a CAMT.053 file, by its IBAN, with the mapping pre-filled when one of your accounts holds that IBAN.

A QIF file whose dates could be day first or month first shows the choice in the review: pick the order the file uses and the rows are read again before you import.

An import you don't finish expires after seven days. Seven days after an import, WonderMoney deletes the file you uploaded and its row-by-row list; the import keeps only the file's name and how many transactions were imported and skipped, and the imported transactions stay in the account.

The mobile app has the same review before anything is imported: rows are listed by kind, possible duplicates are skipped unless you include them, a QIF file with ambiguous dates asks for the order, and a file with several accounts asks where each one goes. It has no column preview: an account at one of the banks listed above takes that bank's own CSV or Excel export; for any other account, the app asks for a CSV in the WonderMoney template, which the import screen describes and shares. OFX/QFX, QIF and CAMT.053 files work in both cases.

## Possible duplicates

The same purchase often arrives twice: once from bank sync and once from a file, a day apart or with a different description. A row of the file that nothing identifies as already imported is a possible duplicate when the account it goes to holds a transaction with the same amount, money in or money out, in the same currency, dated up to 3 days before or after it. The review shows the row beside that transaction, with the date, description and amount of each, so you can compare them.

- When several transactions in the account could be the row, none of them is matched, and the review says so. When only one of them names the same merchant, that one is matched.
- One transaction in the account answers for one row only. Two identical coffees in the file against one in the account leave one row a possible duplicate and the other new.
- Only the account the row goes to is checked, and only transactions you can see on it. Deleted transactions do not count; hidden ones do.
- A possible duplicate is skipped unless you include it, and nothing is dropped without your choice: tick it and the import adds it as a new transaction.
- In a file with several accounts, each row is checked against the account you chose for it, and checked again when you change that choice.

## Review

After import, compare the number of rows and the first few balances with the source file. If the file covers a long period, check that the dates were interpreted correctly.

Imported rows are categorized using the same deterministic categorizer as synced transactions, so the reason you see on a suggestion is consistent no matter how the transaction arrived. When you bulk-categorize imported rows, the chosen category is written to each transaction and the merchant mapping is updated for future imports.

## Common issues

- The file uses an unexpected date format.
- Amounts are stored with the wrong decimal separator.
- Credits and debits are reversed.
- The same data was already imported from another source.
- The OFX/QFX file is an investment statement, or holds only a balance. WonderMoney skips it and says so in the import.
- The QIF file's dates could be day first or month first, and the import asks which before it can go on.
- The QIF file is an investment export (`!Type:Invst`). WonderMoney skips those records and says so in the import.
- The CAMT.053 file declares a document type (`DOCTYPE`). WonderMoney refuses the file instead of reading it.

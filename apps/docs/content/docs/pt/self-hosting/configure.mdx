Toda a configuração está no ficheiro `.env`, ao lado do `docker-compose.yml`, comentada secção a secção. Depois de o editares, aplica as alterações com:

```sh
docker compose up -d
```

## Endereços e segredos

O `generate-env.sh`, que o script de instalação executa, escreve estes valores uma vez. A API não arranca sem eles.

| Definição | O que é |
|---|---|
| `APP_URL`, `API_URL` | Os endereços públicos da aplicação web e da API. Vê [HTTPS e domínios](/pt/docs/self-hosting/https-and-domains) |
| `POSTGRES_PASSWORD` | A palavra-passe da base de dados Postgres incluída, definida quando a base de dados é criada pela primeira vez |
| `BETTER_AUTH_SECRET` | O segredo de início de sessão, que protege as sessões |
| `CREDENTIAL_ENCRYPTION_KEY_V1` | Cifra as credenciais bancárias guardadas de cada utilizador. Nunca a alteres depois de estar em uso, e guarda uma cópia separada das cópias de segurança da base de dados: sem ela, uma base de dados restaurada é ilegível |
| `EMAIL_OPT_OUT_SIGNING_SECRET` | Assina as ligações para cancelar a subscrição nos emails. O worker cria-as e a API verifica-as, por isso ambos precisam do mesmo valor |
| `ADMIN_API_KEY` | A chave dos endpoints de administração, enviada no cabeçalho `x-api-key` (vê [Estado da sincronização bancária](/pt/docs/self-hosting/bank-sync-health)) |
| `INTERNAL_SERVICE_API_KEY` | Uma chave de serviço interna que a API exige no arranque. Mantém o valor gerado |

Algumas definições do `.env` estão descritas noutras páginas:

- `TRUST_PROXY`, `BIND_ADDRESS`, `AUTH_COOKIE_DOMAIN`, `NEXT_PUBLIC_AUTH_COOKIE_DOMAIN` e o perfil `proxy` em `COMPOSE_PROFILES`: [HTTPS e domínios](/pt/docs/self-hosting/https-and-domains).
- `WM_VERSION`, `WM_IMAGE_REGISTRY`, `BACKUP_DIR`, `BACKUP_SCHEDULE`, `BACKUP_KEEP_DAYS`, `BACKUP_TZ`, `BACKUP_DESTINATION`, `BACKUP_OFFSITE_SCHEDULE` e `BACKUP_OFFSITE_KEEP_DAYS`: [Atualizações e cópias de segurança](/pt/docs/self-hosting/upgrade-and-backup).
- `HEALTH_MAX_JOB_AGE_MINUTES`: [Monitorização](/pt/docs/self-hosting/monitoring).
- `IOS_APP_TEAM_ID`, `IOS_APP_BUNDLE_ID`, `ANDROID_APP_PACKAGE` e `ANDROID_APP_CERT_SHA256`: [Usar a aplicação móvel com o teu servidor](/pt/docs/self-hosting/mobile-app).

## Email

Indica um servidor SMTP:

```sh
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_USER=...
SMTP_PASSWORD=...
EMAIL_FROM=money@example.com
```

Ou define `RESEND_API_KEY` para usar o Resend. Para testar sem um fornecedor real, usa o Mailpit incluído: acrescenta `mail` a `COMPOSE_PROFILES`, define `SMTP_HOST=mailpit` e `SMTP_PORT=1025`, corre `docker compose up -d` e lê os emails em http://localhost:8025.

O `SMTP_PORT` é `587` por omissão. A ligação usa TLS implícito na porta 465 e, nas restantes, STARTTLS quando o servidor o oferece; define `SMTP_SECURE` como `true` ou `false` para escolheres tu.

A API escolhe o fornecedor a partir do que está definido: o Resend quando `RESEND_API_KEY` está definida, caso contrário SMTP quando `SMTP_HOST` está. Para escolheres tu, define `EMAIL_DRIVER` como `smtp`, `resend` ou `log`; `log` escreve cada mensagem no registo da API em vez de a enviar. `EMAIL_FROM_NAME` define o nome do remetente, que é o `INSTANCE_NAME` quando está vazio.

Sem um fornecedor configurado, a API escreve cada mensagem no seu registo e o worker não envia lembretes em segundo plano (lembretes de pagamento do cartão, expiração de tokens de API). Os lembretes de pagamento do cartão saem alguns dias antes do vencimento de um extrato: define `CREDIT_CARD_DUE_REMINDER_DAYS` no worker para mudar a antecedência (3 por omissão, um número inteiro de dias).

## Armazenamento de ficheiros

As importações CSV e as cópias de recibos precisam de armazenamento compatível com S3. Para usar o armazenamento incluído ([SeaweedFS](https://github.com/seaweedfs/seaweedfs)), define estes valores no `.env` e corre `docker compose up -d`:

```sh
COMPOSE_PROFILES=storage
AWS_ACCESS_KEY_ID=escolhe-um-utilizador
AWS_SECRET_ACCESS_KEY=escolhe-uma-palavra-passe-longa
S3_ENDPOINT=http://storage:8333
S3_PUBLIC_ENDPOINT=http://localhost:9000
S3_BUCKET=wondermoney
```

As duas chaves passam a ser as credenciais do armazenamento, que não arranca sem elas. O `S3_PUBLIC_ENDPOINT` é o endereço que os navegadores usam para chegar ao armazenamento; atrás de um proxy, dá-lhe um nome próprio com HTTPS que encaminhe para a porta 9000. Qualquer serviço compatível com S3 também funciona, como Cloudflare R2, Backblaze B2 ou AWS S3: define `S3_REGION` quando o serviço o exigir (com `S3_ENDPOINT` definido e a região vazia, usa-se `us-east-1`). Com `S3_ENDPOINT`, os pedidos usam endereços no estilo de caminho (path-style); define `S3_FORCE_PATH_STYLE=false` para um serviço que só aceite o estilo de anfitrião virtual. Os anexos das transações usam o mesmo armazenamento: sem ele, a secção de anexos fica oculta e os seus endpoints respondem 503.

## Funcionalidades de IA

A leitura de recibos, o mapeamento de colunas CSV, a importação de extratos em PDF, a categorização de transações, o resumo mensal e o assistente funcionam com qualquer endpoint compatível com OpenAI: OpenAI, OpenRouter, ou um modelo a correr localmente com Ollama, LM Studio ou vLLM.

```sh
AI_BASE_URL=http://host.docker.internal:11434/v1
AI_MODEL=llama3.1
```

Define `AI_API_KEY` quando o endpoint exigir uma chave. Para usares um modelo diferente numa funcionalidade, define `AI_MODEL_<FUNCIONALIDADE>`; por exemplo, a leitura de recibos precisa de um modelo que leia imagens, definido com `AI_MODEL_OCR`. As funcionalidades são `ASSISTANT`, `CSV_MAPPING`, `ENRICHMENT` (categorização de transações), `MONTHLY_STORY`, `OCR` e `STATEMENT_IMPORT`. As definições são `AI_MODEL_ASSISTANT`, `AI_MODEL_CSV_MAPPING`, `AI_MODEL_ENRICHMENT`, `AI_MODEL_MONTHLY_STORY`, `AI_MODEL_OCR` e `AI_MODEL_STATEMENT_IMPORT`.

Para usares a Anthropic com a tua própria chave de API, escolhe-a explicitamente:

```sh
AI_PROVIDER=anthropic
ANTHROPIC_API_KEY=sk-ant-...
AI_MODEL=claude-sonnet-4-5
```

`AI_MODEL`, ou `AI_MODEL_<FUNCIONALIDADE>` para uma funcionalidade, é obrigatório: não há modelo predefinido. A leitura de recibos precisa de um modelo que leia imagens, por isso define `AI_MODEL_OCR` se o teu modelo predefinido não o fizer. A Anthropic tem prioridade sobre `AI_BASE_URL`, mas uma configuração Azure completa continua a ter precedência. Vê [Azure](#azure).

A [importação de extratos em PDF](/pt/docs/accounts-transactions/import-pdf-statements) envia cada página do extrato ao modelo como imagem, por isso precisa de um modelo que leia imagens. Num endpoint compatível com OpenAI fica desligada até indicares um com `AI_MODEL_STATEMENT_IMPORT`; o `AI_MODEL` não é usado para ela, porque um modelo local predefinido muitas vezes só lê texto. Na Anthropic usa `AI_MODEL_STATEMENT_IMPORT`, ou `AI_MODEL` quando esse estiver vazio. A aplicação diz à pessoa qual é o fornecedor antes de enviar qualquer página: a Anthropic ou o Azure OpenAI pelo nome, um endpoint compatível com OpenAI como o fornecedor de IA configurado no servidor. O endereço do endpoint nunca é mostrado, e `GET /v1/instance` indica apenas o tipo de fornecedor.

| Definição | O que faz |
|---|---|
| `AI_MODEL_STATEMENT_IMPORT` | O modelo que lê os extratos em PDF. Obrigatório num endpoint compatível com OpenAI |
| `AI_DAILY_LIMIT_STATEMENT_IMPORT` | Extratos em PDF que um agregado pode importar por dia; cada extrato conta como um, tenha as páginas que tiver. Vazio significa sem limite |
| `STATEMENT_IMPORT_MAX_BYTES` | O maior PDF aceite, em bytes. Por omissão `10485760` (10 MB) |
| `STATEMENT_IMPORT_MAX_PAGES` | O número máximo de páginas de um extrato. Cada página é um pedido ao modelo, por isso também limita quanto custa um extrato. Por omissão `20` |

Define os dois limites na API e no worker; um valor que não seja um número inteiro positivo impede-os de arrancar.

Se o registo estiver aberto e pagares pelo modelo, define `AI_REQUIRES_VERIFIED_EMAIL=true`. As contas criadas com email e palavra-passe recebem então um link de verificação por email, e têm de o seguir antes de poderem usar o assistente, a leitura de recibos, o mapeamento de colunas com IA ou a importação de extratos em PDF. As contas Google e Apple contam como verificadas. É preciso ter o email configurado.

Para limitar o que cada agregado pode gastar no modelo por dia, define `AI_DAILY_LIMIT_ASSISTANT` (mensagens ao assistente), `AI_DAILY_LIMIT_OCR` (leituras de recibos) e `AI_DAILY_LIMIT_CSV_MAPPING` (importações CSV mapeadas pelo modelo). Os membros de um agregado partilham o limite, que é reposto à meia-noite UTC. Deixa-os vazios para não haver limite. Quando um agregado chega a um limite, a aplicação avisa até ao dia seguinte; as importações CSV continuam a funcionar, com as colunas mapeadas à mão.

### Azure

O Azure OpenAI e o Azure AI Foundry são decididos funcionalidade a funcionalidade. Uma funcionalidade com todas as suas definições de Azure presentes usa o Azure, independentemente de `AI_PROVIDER` e `AI_BASE_URL`; uma funcionalidade a que falte alguma recorre à Anthropic ou ao endpoint compatível com OpenAI, ou fica desligada.

| Definição | O que faz |
|---|---|
| `AZURE_OPENAI_ENDPOINT`, `AZURE_OPENAI_API_KEY`, `AZURE_OPENAI_API_VERSION` | O teu recurso Azure OpenAI, a sua chave e a versão da API a chamar. As três são necessárias para o assistente, a leitura de recibos, o mapeamento de colunas de CSV, a história mensal e a importação de extratos em PDF |
| `AZURE_OPENAI_DEPLOYMENT` | O deployment que o assistente usa. Sem ele, o assistente não usa o Azure |
| `AZURE_OPENAI_OCR_DEPLOYMENT` | O deployment que lê recibos; tem de ler imagens. Sem ele, a leitura de recibos não usa o Azure |
| `AZURE_OPENAI_STATEMENT_IMPORT_DEPLOYMENT` | O deployment que lê extratos em PDF; tem de ler imagens. Sem ele, a importação de extratos em PDF não usa o Azure |
| `AZURE_AI_FOUNDRY_ENDPOINT`, `AZURE_AI_FOUNDRY_API_KEY`, `AZURE_AI_FOUNDRY_API_VERSION` | O teu recurso Azure AI Foundry, apenas para a categorização de transações. As três são necessárias |

Dois nomes estão fixos no código. No Azure OpenAI, o mapeamento de colunas de CSV e a história mensal chamam um deployment chamado `gpt-5.4-nano`, por isso o recurso precisa de um deployment com esse nome. No Azure AI Foundry, a categorização de transações chama o modelo `DeepSeek-V4-Flash`; define `TRANSACTION_ENRICHMENT_GPT_MODEL_VERSION` no worker para indicares outro. Define as definições de Azure na API e no worker.

## Dados de mercado

Define `EODHD_API_KEY` para ligar a pesquisa de tickers, as cotações em tempo real e o módulo de Mercados Financeiros.

`MARKET_DATA_PROVIDERS` indica os fornecedores de dados de mercado a consultar, por ordem, separados por vírgulas. Vazio significa só `eodhd`. Quando um fornecedor falha ou não tem nada para um título, é consultado o seguinte da lista, e uma funcionalidade que nenhum fornecedor da lista oferece fica escondida. Um fornecedor desconhecido ou repetido impede a API e o worker de arrancar. Define-o em ambos.

| Fornecedor | O que dá | Precisa de |
|---|---|---|
| `eodhd` | Pesquisa, últimas cotações, histórico diário, dividendos e desdobramentos, na maioria das bolsas | `EODHD_API_KEY` |
| `stooq` | O último fecho diário e o histórico diário de títulos cotados nos EUA, em Londres, na Xetra e em Tóquio, e dos principais índices dos EUA. Sem pesquisa, dividendos nem desdobramentos | Nada |
| `coingecko` | Pesquisa de criptomoedas, últimas cotações e até um ano de histórico diário, para pares escritos como `BTC-USD` | Nada |

`MARKET_DATA_PROVIDERS=eodhd,stooq,coingecko` consulta primeiro a EODHD e os fornecedores gratuitos quando esta não consegue responder. `MARKET_DATA_PROVIDERS=stooq,coingecko` dá cotações às posições sem chave da EODHD; os títulos passam a ser encontrados só pela pesquisa de criptomoedas da CoinGecko, por isso as ações têm de já estar no teu catálogo.

A Stooq e a CoinGecko são serviços externos com os seus próprios termos de utilização, e ficam desligados até os pores na lista. Lê os termos antes de o fazeres: és responsável por cumpri-los, incluindo eventuais limites de pedidos e de uso comercial. O serviço alojado do WonderMoney não os usa.

Cada cotação guardada regista o fornecedor de onde veio. O histórico de cotações de uma posição mostra-o, e os administradores veem os fornecedores e as cotações recentes de cada um em `GET /v1/admin/market-data/sources`.

## Carteiras de criptomoedas

As [carteiras de criptomoedas](/pt/docs/portfolio-investments/crypto-wallets) avaliam a Bitcoin e a Ethereum que os teus utilizadores guardam em endereços públicos. Estão desligadas por omissão: nenhum explorador é contactado, e as aplicações não as oferecem. Cada rede liga-se quando indicas o explorador de blocos de onde o servidor lê os saldos.

| Definição | O que leva |
|---|---|
| `CRYPTO_BTC_EXPLORER_URL` | A raiz REST de uma API compatível com mempool.space ou Esplora, por exemplo `https://mempool.example.org/api`. O servidor pede `<url>/address/<address>` para cada endereço Bitcoin, incluindo cada um derivado de uma chave pública estendida |
| `CRYPTO_ETH_EXPLORER_URL` | A raiz de uma instância Blockscout, por exemplo `https://blockscout.example.org`. O servidor pede `<url>/api/v2/addresses/<address>` e `<url>/api/v2/addresses/<address>/token-balances` para cada endereço Ethereum |

Cada uma tem de ser um endereço `https` sem nome de utilizador, palavra-passe, query nem fragmento; qualquer outra coisa impede a API e o worker de arrancar. Define-as em ambos. A API só oferece carteiras para as redes que têm explorador, e `GET /v1/instance` indica-as em `features.cryptoWalletChains`. O worker sincroniza todas as carteiras uma vez por dia às 04:30 UTC, e de novo quando um membro cria uma carteira, adiciona um endereço, marca um token ou escolhe Sincronizar agora. Faz um pedido de cada vez a cada explorador, espaçados, com um limite de 15 segundos, e tenta até três vezes após um limite de tempo esgotado, um erro do servidor ou um `429` (esperando o que `Retry-After` pedir, até 30 segundos).

O explorador vê cada endereço pelo qual é questionado e o endereço IP do teu servidor, e como é um só servidor a perguntar por todos os endereços de um agregado, consegue ligá-los entre si. Nada mais é enviado: nem nomes, nem montantes, nem identificadores de utilizadores. A escolha privada é um nó Bitcoin ou Ethereum teu com um explorador à frente: [mempool](https://github.com/mempool/mempool) ou [Esplora](https://github.com/Blockstream/esplora) para Bitcoin, [Blockscout](https://github.com/blockscout/blockscout) para Ethereum. Há instâncias públicas, como `https://mempool.space/api` e `https://eth.blockscout.com`. São serviços externos com os seus próprios termos de utilização e limites de pedidos: usar uma é escolha tua, cumprir os seus termos é responsabilidade tua, e a tua política de privacidade deve dizer que os endereços dos teus utilizadores lhe são enviados. O serviço alojado do WonderMoney não liga as carteiras de criptomoedas.

Os preços vêm dos fornecedores em `MARKET_DATA_PROVIDERS` ([Dados de mercado](#dados-de-mercado)): cada token é procurado pelo símbolo face ao dólar americano, como `<SYMBOL>-USD.CC`. A EODHD e a CoinGecko dão ambas preços de criptomoedas. Sem um fornecedor que os dê, as carteiras mostram os saldos mas não têm valor. Os tokens ERC-20 têm preço pelo símbolo, por isso um token pode fazer-se passar por outro; os membros marcam os tokens que querem contar, e a aplicação diz-lhes para marcarem só os que reconhecem.

## Logótipos de comerciantes

Os logótipos de comerciantes estão desligados por omissão. Cada comerciante mostra então a primeira letra do nome num círculo de cor, e nada sobre os comerciantes dos teus utilizadores sai do servidor.

Define `MERCHANT_LOGO_URL_TEMPLATE` com o endereço de um serviço de logótipos, com `{domain}` onde entra o domínio do site do comerciante, por exemplo `https://logos.example.com/{domain}.png`. Tem de ser um endereço `https`, e `{domain}` tem de vir depois do anfitrião; outro valor impede a API de arrancar. Define-o na API.

Quando um membro adiciona um site a um comerciante, a API pede ao serviço o logótipo desse domínio, guarda-o durante um dia (um domínio sem logótipo durante uma hora) e serve-o às aplicações web e móvel a partir do teu próprio servidor. O serviço vê o endereço do teu servidor e o domínio do comerciante, como `example.com`. Nunca vê os endereços, os navegadores, as contas nem as transações dos teus utilizadores, e as aplicações nunca o contactam. Escolhe um serviço cujos termos aceites para isso, e indica-o na tua política de privacidade.

Um endereço de logótipo que um membro escreva ele próprio tem prioridade sobre o modelo. As aplicações carregam essa imagem diretamente do endereço escolhido pelo membro, sem referenciador, pelo que esse site vê o endereço de cada membro do agregado que a vê. Só são aceites endereços `https` com um nome de anfitrião.

## Notificações push

As notificações push estão desligadas por predefinição. Define `PUSH_ENABLED=true` na API e no worker para que a aplicação móvel possa registar telemóveis e receber notificações através do serviço de push da Expo: alertas de orçamento, lembretes de pagamento do cartão, alertas de ligações bancárias e uma notificação de teste. Cada categoria fica desligada até que a pessoa a ligue na aplicação, e só nesse momento o telemóvel pede autorização.

O texto diz o que aconteceu, nunca quanto: "O teu orçamento Supermercado ultrapassou o plano" ou "Um pagamento de cartão vence daqui a 3 dias". Os valores, saldos e comerciantes ficam na aplicação. A Expo recebe o token de push de cada telemóvel registado, o título e o texto da notificação e o ecrã da aplicação que ela abre.

Se o projeto Expo a partir do qual a aplicação foi compilada exigir um token de acesso nos pedidos de push, define `EXPO_ACCESS_TOKEN` na API e no worker. As versões da aplicação que o teu servidor consegue alcançar dependem desse projeto; consulta [Notificações push](/pt/docs/self-hosting/mobile-app#notificações-push).

## Sincronização bancária

A sincronização com bancos europeus não precisa de configuração no servidor. Cada pessoa adiciona a sua própria chave de aplicação Enable Banking nas Definições, por isso as credenciais bancárias nunca são partilhadas entre utilizadores.

`BANK_PROVIDERS` lista os fornecedores bancários que a tua instância oferece, separados por vírgulas. Não definida ou vazia significa todos os fornecedores incluídos exceto os opcionais, o que hoje é só `enable_banking`. Define-a na API e no worker.

| Fornecedor | O que liga | Precisa de |
|---|---|---|
| `enable_banking` | Bancos na Europa, através da aplicação Enable Banking de cada pessoa ou da do servidor | Nada no servidor, ou uma aplicação Enable Banking para todo o servidor ([abaixo](#uma-aplicação-enable-banking-para-o-servidor)). Ligado, a não ser que `BANK_PROVIDERS` o deixe de fora |
| `simplefin` | Bancos dos Estados Unidos e do Canadá, através do SimpleFIN Bridge, um serviço pago que cada pessoa subscreve | Opcional: desligado até estar na lista, como em `BANK_PROVIDERS=enable_banking,simplefin`. Vê [SimpleFIN](/pt/docs/self-hosting/simplefin) |

Um identificador que esta versão não tenha é ignorado, por isso `BANK_PROVIDERS=none` desliga a sincronização bancária. `GET /v1/instance` indica os fornecedores ligados em `features.bankSyncProviders`, e as aplicações só oferecem esses.

| Definição | O que faz |
|---|---|
| `SIMPLEFIN_BRIDGE_HOSTS` | Os anfitriões que o servidor pode contactar para o SimpleFIN, separados por vírgulas. Vazio significa o SimpleFIN Bridge, `bridge.simplefin.org` e `beta-bridge.simplefin.org`. Define-a só para outro servidor que fale o protocolo SimpleFIN; substitui a lista por omissão. Cada endereço SimpleFIN tem de ser `https` na porta 443, estar num destes anfitriões e resolver só para endereços públicos ([SimpleFIN](/pt/docs/self-hosting/simplefin#privacidade-e-segurança)). Define-a na API e no worker |

O worker sincroniza cada ligação bancária no máximo uma vez a cada `BANK_SYNC_MIN_INTERVAL_HOURS` horas, 20 por omissão. Ao abrigo da PSD2, um banco pode limitar o acesso não assistido a quatro chamadas por dia por conta, por isso define-a como `6` ou mais para ficares dentro desse limite. O SimpleFIN Bridge espera cerca de 24 pedidos por dia ou menos por ligação, por isso não a baixes muito se ofereceres o SimpleFIN. Uma sincronização falhada espera o mesmo intervalo antes da tentativa seguinte. Define-a no worker; um valor que não seja um número positivo impede o worker de arrancar.

### Uma aplicação Enable Banking para o servidor

Para que o teu agregado possa ligar bancos sem que cada pessoa registe uma aplicação, regista tu uma na Enable Banking e indica ao servidor o ID da aplicação e a chave privada:

| Definição | O que faz |
|---|---|
| `ENABLE_BANKING_APP_ID` | O ID da aplicação. Liga a aplicação do servidor em conjunto com o ficheiro da chave |
| `ENABLE_BANKING_PRIVATE_KEY_FILE` | A chave privada da aplicação (o ficheiro `.pem` que geraste ao registá-la, não o certificado). Com Docker Compose, o caminho no servidor, como `./enable-banking.pem` ao lado de `docker-compose.yml`: a API e o worker leem-no como um segredo Docker. Noutros casos, o caminho de onde a API e o worker o leem |
| `ENABLE_BANKING_PRODUCTION_CONTRACT` | `true` levanta o limite de um agregado descrito abaixo. Define-a só depois de a Enable Banking te dar um contrato de produção completo |

Os contentores correm como o utilizador `1000`, por isso esse utilizador tem de conseguir ler o ficheiro da chave: `chmod 644 enable-banking.pem` ou `chown 1000 enable-banking.pem`. No Kubernetes, guarda a chave num Secret e indica-o em `enableBanking.privateKeySecret` nos valores do chart. Define as três na API e no worker.

Ambos verificam a chave ao arrancar: um ficheiro que não conseguem ler, ou que não seja uma chave privada RSA, impede-os de arrancar com um erro que indica o ficheiro. A chave nunca é registada nos logs, guardada na base de dados nem enviada às aplicações. `GET /v1/instance` indica `features.bankSyncCredentials: "instance"` (`"user"` sem ela), e as aplicações web e móvel saltam o passo "adiciona a tua chave" para todos os que a aplicação abrange.

Quem adicionar a sua própria chave nas Definições continua a ligar bancos com a sua. Cada ligação mantém a aplicação com que foi feita: se removeres ou substituíres a aplicação do servidor, as ligações feitas com ela deixam de sincronizar e os seus donos voltam a ligar-se.

### O limite da licença: um agregado

Uma aplicação Enable Banking nova funciona em modo Restricted Production, em que só pode ligar as contas de quem a registou. Sem um contrato de produção completo, a aplicação do servidor serve por isso um agregado:

- Enquanto o servidor tiver um único agregado, todos os seus membros podem ligar bancos com ela.
- O primeiro agregado a ligar um banco com ela mantém-na, para novas ligações e para voltar a ligar, depois de outros agregados se registarem. As suas ligações continuam a sincronizar.
- Os outros agregados veem o passo habitual "adiciona a tua própria chave", com uma linha a explicar que a ligação partilhada do servidor só serve um agregado.
- Se um segundo agregado se registar antes de alguém ligar um banco, nenhum agregado recebe a aplicação do servidor até definires `ENABLE_BANKING_PRODUCTION_CONTRACT=true`.

A conta de demonstração nunca conta. A própria Enable Banking também aplica o limite: em modo Restricted Production, recusa contas que não sejam do dono da aplicação, incluindo as das outras pessoas do seu agregado. Confirma no Control Panel da Enable Banking a que contas a tua aplicação pode aceder.

## Início de sessão com Google

Define `GOOGLE_CLIENT_ID` e `GOOGLE_CLIENT_SECRET` (de um cliente OAuth no Google Cloud, com `<API_URL>/api/auth/callback/google` como URI de redirecionamento autorizado) para mostrares "Continuar com Google" nas páginas de início de sessão e de registo. Sem os dois, o botão fica escondido.

## Iniciar sessão com a Apple

O início de sessão com a Apple funciona apenas na aplicação para iOS; a aplicação web não tem botão da Apple. A aplicação para iOS mostra o botão em todos os servidores, por isso, até configurares isto, quem tocar nele no teu servidor é informado de que o início de sessão não está disponível.

Define `APPLE_NATIVE_AUDIENCE` na API com o bundle ID da aplicação para iOS que os teus utilizadores usam: `money.wonder.app` para a aplicação publicada, ou o bundle ID de uma aplicação compilada por ti. A API passa a aceitar o token de identidade que a Apple emite para essa aplicação, e verifica-o com as chaves públicas da Apple. Aceita um único bundle ID, sem espaços nem carateres universais; qualquer outra coisa impede a API de arrancar. Uma conta nova criada desta forma segue o `SIGNUP_MODE`.

`APPLE_CLIENT_ID` e `APPLE_CLIENT_SECRET` (um Services ID da Apple e o respetivo segredo de cliente, um token assinado que geras tu) registam na API o início de sessão da Apple pelo navegador. Nenhuma página da aplicação web o usa, por isso deixa-as vazias. `APPLE_CLIENT_SECRET` sem `APPLE_CLIENT_ID` impede a API de arrancar.

## Início de sessão único (OIDC)

Inicia sessão através do teu próprio fornecedor de identidade, como o Authentik ou o Keycloak: as páginas de início de sessão e de registo, na web e na aplicação móvel, mostram então `Iniciar sessão com <nome>`. [Início de sessão único](/pt/docs/self-hosting/single-sign-on) explica como configurar o fornecedor.

| Definição | O que faz |
|---|---|
| `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET` | O URL do emissor do fornecedor (HTTPS) e o cliente que lá registaste, com `<API_URL>/api/auth/callback/oidc` como URI de redirecionamento. Os três ligam o início de sessão único em conjunto; qualquer outra definição `OIDC_` sem eles impede a API de arrancar |
| `OIDC_DISPLAY_NAME` | O nome no botão. Por omissão, `SSO` |
| `OIDC_SCOPES` | Os âmbitos a pedir, separados por espaços; tem de incluir `openid`. Por omissão, `openid email profile` |
| `OIDC_GROUPS_CLAIM` | A claim que lista os grupos da pessoa. Por omissão, `groups` |
| `OIDC_ALLOWED_GROUPS` | Grupos separados por vírgulas. Quando definida, só os seus membros (e os membros dos grupos de administração) podem iniciar sessão |
| `OIDC_ADMIN_GROUPS` | Grupos separados por vírgulas cujos membros são administradores da instância. Verificado em cada início de sessão, por isso sair do grupo retira a administração |
| `OIDC_AUTO_SIGNUP` | `true` cria a conta no primeiro início de sessão através do fornecedor mesmo quando `SIGNUP_MODE` é `invite` ou `closed`. O registo com palavra-passe continua a seguir `SIGNUP_MODE` |
| `OIDC_ONLY` | `true` desliga o início de sessão, o registo e a reposição com palavra-passe, e esconde-os nas aplicações. As chaves de acesso continuam a funcionar |
| `OIDC_TRUST_IDP_MFA` | `true` dispensa o código do autenticador do WonderMoney depois de um início de sessão através do fornecedor. Define-a só quando o próprio fornecedor exige um segundo fator |
| `OIDC_ALLOW_UNVERIFIED_EMAIL` | `true` aceita um endereço de email que o fornecedor não verificou. Desligada por omissão; uma conta assim nunca é ligada a uma conta existente |

`GET /v1/instance` indica `features.oidc: { "name": "<OIDC_DISPLAY_NAME>" }` e, com `OIDC_ONLY`, `features.passwordSignIn: false`.

## Chaves de acesso

As chaves de acesso (passkeys) não precisam de nenhuma variável de ambiente. Pertencem ao domínio em `APP_URL`, o endereço da aplicação web, e o navegador só as oferece nesse domínio. Funciona da mesma forma quer a aplicação web e a API partilhem um domínio, quer usem dois, como `money.example.com` e `api.money.example.com`.

Os navegadores só permitem chaves de acesso por HTTPS, ou em `http://localhost`. Um endereço IP como `http://192.168.1.10:3000` não funciona: dá à aplicação web um domínio com HTTPS (consulta [HTTPS e domínios](/pt/docs/self-hosting/https-and-domains)).

Se a aplicação web mudar para outro domínio, as chaves de acesso existentes deixam de funcionar e os teus utilizadores têm de as adicionar outra vez. As palavras-passe continuam a funcionar. `GET /v1/instance` reporta `features.passkey: true`.

## A tua instância

| Definição | O que faz |
|---|---|
| `INSTANCE_NAME` | O nome da tua instância. A aplicação web mostra-o nos títulos dos separadores do navegador, nas pré-visualizações de links e nas páginas de início de sessão e de registo, e no lugar do logótipo do WonderMoney quando o alteras. Cada email usa-o no assunto, no texto e na assinatura, e como nome do remetente se `EMAIL_FROM_NAME` não estiver definido; as aplicações de autenticação mostram-no como etiqueta. A aplicação web lê-o da API, por isso define-o só na API; uma alteração aparece na aplicação web em até cinco minutos |

| `HOUSEHOLD_MAX_MEMBERS` | O número máximo de pessoas num agregado, incluindo o titular. Um convite pendente ocupa um lugar até ser aceite, revogado ou expirar. Por omissão `6`; um número inteiro positivo. Define-o na API; um valor que não seja um número inteiro positivo impede-a de arrancar |
| `SUPPORT_EMAIL` | A caixa de correio do formulário de contacto, dos alertas de conta e do feedback na aplicação, e o endereço de suporte que a aplicação mostra; deixa vazio para os desligar e esconder as ligações de suporte. O formulário "Partilhar Feedback" também precisa de email configurado; sem ele, o formulário fica escondido |
| `SPONSOR_URL` | Uma página onde os teus utilizadores podem contribuir para manter a instância (Open Collective, GitHub Sponsors, ...). As perguntas frequentes da aplicação web incluem a ligação quando está definida |
| `NEXT_PUBLIC_TERMS_URL`, `NEXT_PUBLIC_PRIVACY_URL` | As tuas páginas legais, ligadas a partir da página de registo quando ambas estão definidas |
| `PRIVACY_POLICY_URL` | A tua política de privacidade, ligada a partir do rodapé dos emails. `{lang}` é substituído pelo idioma do destinatário (`en`, `pt` ou `es`), por exemplo `https://example.com/{lang}/privacy`. Por omissão, aponta para as definições de privacidade da aplicação |
| `MCP_ENABLED` | O servidor MCP só de leitura em `POST /v1/mcp`, que permite a um cliente de IA perguntar pelas finanças do próprio utilizador com um token de API pessoal com `mcp:read` (consulta [Ligar um cliente de IA](/pt/docs/settings-security-privacy/connect-ai-client)). Ligado por omissão; define `false` para responder `404` e reportar `features.mcp: false` em `GET /v1/instance` |
| `DEMO_SIGN_IN_ENABLED` | `true` liga uma demonstração pública só de leitura: um botão **Experimentar a demonstração** que inicia a sessão de qualquer pessoa numa conta de demonstração partilhada. Desligado por omissão; consulta [Demonstração pública](#demonstração-pública) |
| `TRANSFER_MATCH_FX_TOLERANCE` | A diferença aceite entre os dois lados de uma transferência entre contas em moedas diferentes, depois de converter o valor que saiu à taxa de câmbio desse dia, como fração do valor que chegou: `0.02` (por omissão) é 2 por cento. Aumenta-a se a margem cambial e as comissões do teu banco forem maiores; no máximo `0.25`. Define-a na API e no worker |
| `MIN_APP_VERSION` | A versão mais antiga da aplicação móvel que se pode ligar, por exemplo `1.0.3`. Uma aplicação mais antiga recebe o aviso para atualizar quando alguém introduz o endereço do teu servidor. Vazio significa qualquer versão. `GET /v1/instance` indica-a em `minAppVersion` |
| `MCP_TOOL_CALLS_PER_MINUTE` | Quantas chamadas a ferramentas MCP um token pode fazer por minuto. Por omissão, `60`. Define-a na API |
| `CORS_ALLOWED_ORIGINS` | As origens de navegador que podem chamar a API, separadas por vírgulas, por exemplo `https://money.example.com,https://other.example.com`. Vazio significa a origem de `APP_URL`, que é tudo o que uma instalação normal precisa. Um valor substitui essa predefinição, por isso inclui a origem da própria aplicação web. Define-a na API |
| `NEXT_PUBLIC_DOCS_URL` | Para onde apontam as ligações de ajuda e documentação da aplicação web. Vazio significa `https://docs.wonder.money`. Define-a com a tua própria cópia desta documentação, se alojares uma |
| `TRANSACTION_BAYES_CATEGORIZATION_ENABLED` | As transações novas são categorizadas no servidor a partir das escolhas anteriores de cada pessoa, sem nenhum fornecedor de IA e também para quem ocultou as funcionalidades de IA. Ligado por omissão; `false` desliga-o. `TRANSACTION_BAYES_MIN_POSTERIOR` (por omissão `0.8`) e `TRANSACTION_BAYES_MIN_MARGIN` (por omissão `0.2`) definem a certeza necessária para atribuir uma categoria, cada uma um número de 0 a 1 |

## Demonstração pública

Se a tua instância ligar a demonstração, as pessoas podem experimentar o WonderMoney sem criar conta. Define `DEMO_SIGN_IN_ENABLED=true` na API: a página de início de sessão, na web e na app móvel, passa a mostrar **Experimentar a demonstração**, que inicia a sessão do visitante num agregado de demonstração partilhado, sem palavra-passe, e `GET /v1/instance` reporta `features.demo: true`. Com a definição desligada, `POST /v1/auth/demo` responde `404` e o botão fica escondido.

Todos os visitantes partilham a demonstração, por isso é só de leitura:

- Qualquer alteração é recusada com a mensagem de só leitura: os dados do agregado e a própria conta (nome, email, palavra-passe, autenticador, chaves de acesso e terminar a sessão de outros visitantes).
- Uma sessão de demonstração termina duas horas depois de começar. Os inícios de sessão na demonstração têm um limite por endereço IP, como os inícios de sessão com palavra-passe.
- Uma faixa em todos os ecrãs diz que os dados são uma demonstração partilhada que é reposta todos os dias, com ligações para criar conta (só quando `SIGNUP_MODE` é `open`) e para estes guias de alojamento próprio.
- A conta de demonstração não tem palavra-passe nem autenticador. O início de sessão na demonstração recusa uma conta com autenticador e nunca inicia a sessão noutra conta.

Cria a conta de demonstração e o agregado antes de ligares a definição:

```sh
docker compose exec api node dist/database/scripts/seed-demo-household.js
```

Em Kubernetes, corre o mesmo comando no pod da API. Só escreve a conta de demonstração (`demo@wonder.money`) e o agregado dela, não mexe em mais nenhuma conta e pode ser corrido de novo; corre-o outra vez para repor a demonstração como estava. Recusa, sem alterar nada, quando esse endereço pertence a uma conta que não é a de demonstração. Num servidor sem dados de mercado, dá também um histórico de preços às seis ações da demonstração, mas só a uma ação que não tenha nenhum preço.

Definições recomendadas para uma instância de demonstração:

| Definição | Recomendado | Porquê |
|---|---|---|
| `NEXT_PUBLIC_GTM_ID`, `NEXT_PUBLIC_POSTHOG_KEY`, `ANALYTICS_OUTBOX_MODE` | Vazias | Os visitantes são desconhecidos: nada sobre eles deve ser registado (consulta [Analytics](#analytics)) |
| IA (`AI_BASE_URL`, `AI_PROVIDER`, `AZURE_OPENAI_*`) | Vazias, ou limitadas com `AI_DAILY_LIMIT_*` | A conta de demonstração não pode usar o assistente, a leitura de recibos nem o mapeamento de colunas por IA, porque todos guardam alguma coisa. Com a IA desligada, a app esconde-os. Todos os visitantes partilham um agregado, por isso os limites diários também são partilhados |
| `BANK_PROVIDERS` | `none` | Esconde a sincronização bancária. A conta de demonstração também não consegue ligar um banco |
| `ENABLE_PGBOSS_DEMO_DATA_REFRESH` (worker) | `true` | Avança as transações da demonstração todos os dias às 01:15 UTC, para continuarem recentes |
| `SIGNUP_MODE` | `closed` num servidor só de demonstração, `open` para deixar os visitantes criar conta | A faixa só mostra a ligação para criar conta quando é `open` |

## Analytics

A tua instância não carrega analytics nem gestor de tags, nem regista eventos de utilização, a menos que os ligues. Cada definição abaixo liga um serviço, que envia para a tua própria conta nesse serviço; deixa-as vazias para manter tudo desligado.

| Definição | O que liga |
|---|---|
| `NEXT_PUBLIC_GTM_ID` | O teu contentor do Google Tag Manager (`GTM-XXXXXXX`), carregado em todas as páginas da aplicação web |
| `NEXT_PUBLIC_POSTHOG_KEY` | O PostHog na aplicação web: visualizações de página, eventos de utilização e gravações de sessão, associados ao endereço de email de cada utilizador |
| `ANALYTICS_OUTBOX_MODE=live` com `POSTHOG_API_KEY` | Eventos de registo, início de sessão e sincronização bancária enviados para o PostHog pela API e pelo worker. Define ambos na API e no worker; com o modo desligado, nenhum evento é registado. O `POSTHOG_HOST`, no worker, define o endereço do PostHog, por omissão `https://eu.i.posthog.com` |

Se ligares algum destes, informa os teus utilizadores na tua política de privacidade (`NEXT_PUBLIC_PRIVACY_URL`) e pede consentimento quando a lei o exigir.

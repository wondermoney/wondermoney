---
title: HTTPS e domínios
description: Serve a tua instância por HTTPS num só domínio, ou dá um domínio à aplicação web e outro à API.
---

Antes de usares a tua instância fora da tua rede, serve-a por HTTPS. Um só domínio chega: o proxy incluído serve a aplicação web e a API no mesmo endereço.

## Um só domínio

Adiciona `proxy` a `COMPOSE_PROFILES` no `.env` e define os dois endereços com o mesmo domínio:

```sh
APP_URL=https://money.example.com
API_URL=https://money.example.com
COMPOSE_PROFILES=proxy
TRUST_PROXY=1
BIND_ADDRESS=127.0.0.1
```

Depois corre `docker compose up -d` e aponta o DNS do domínio para a máquina. O proxy é o [Caddy](https://caddyserver.com): obtém e renova o certificado sozinho, envia `/v1/*` e `/api/auth/*` para a API e tudo o resto para a aplicação web.

As portas 80 e 443 têm de estar acessíveis a partir da internet, porque o Caddy responde ao desafio do certificado na 80. `PROXY_HTTP_PORT` e `PROXY_HTTPS_PORT` mudam as portas publicadas.

Não é preciso domínio de cookie: o cookie de sessão pertence a esse único domínio. Deixa `AUTH_COOKIE_DOMAIN` e `NEXT_PUBLIC_AUTH_COOKIE_DOMAIN` vazios.

`BIND_ADDRESS=127.0.0.1` mantém as portas HTTP simples (a aplicação web, a API e, se os usares, o armazenamento e o Mailpit) na máquina, e só o proxy fica acessível de fora.

Para experimentares localmente, define `APP_URL=http://localhost` e `API_URL=http://localhost`: o proxy serve então HTTP simples na porta 80.

## Outro proxy reverso

Qualquer outro proxy reverso funciona: dá-lhe um só domínio e encaminha os mesmos dois prefixos de caminho para a API. Com o Caddy na máquina:

```
money.example.com {
  handle /v1/* {
    reverse_proxy localhost:3001
  }
  handle /api/auth/* {
    reverse_proxy localhost:3001
  }
  handle {
    reverse_proxy localhost:3000
  }
}
```

## Dois domínios

Um domínio para cada continua a funcionar. Dá um nome à aplicação web e outro à API:

```
money.example.com {
  reverse_proxy localhost:3000
}

api.money.example.com {
  reverse_proxy localhost:3001
}
```

Depois, no `.env`:

```sh
APP_URL=https://money.example.com
API_URL=https://api.money.example.com
AUTH_COOKIE_DOMAIN=.example.com
NEXT_PUBLIC_AUTH_COOKIE_DOMAIN=.example.com
TRUST_PROXY=1
```

O domínio do cookie permite que a aplicação web leia a sessão que a API cria, porque estão em subdomínios diferentes do mesmo domínio. O perfil `proxy` incluído serve um só domínio; deixa-o desligado.

## Dizer à API que há um proxy

A API limita quantas vezes cada visitante pode tentar iniciar sessão, e distingue os visitantes pelo endereço IP. Atrás de um proxy, todos os pedidos chegam do endereço do proxy, e o endereço do visitante vem no cabeçalho `X-Forwarded-For`. O `TRUST_PROXY` diz em quantos proxies a API pode confiar:

| Configuração | `TRUST_PROXY` |
|---|---|
| Sem proxy: os navegadores ligam-se diretamente à porta da API | deixa vazio |
| Um proxy reverso (o perfil `proxy` incluído, Caddy, nginx, Traefik, um Cloudflare Tunnel) | `1` |
| O proxy da Cloudflare à frente do teu próprio proxy reverso | `2` |

Em vez de um número, também podes indicar os endereços dos proxies, numa lista separada por vírgulas de endereços IP ou intervalos (por exemplo `172.16.0.0/12`).

Deixa-o vazio quando não há proxy: caso contrário, qualquer pessoa pode escrever o seu próprio `X-Forwarded-For` e contornar os limites. Define-o quando há um: caso contrário, todos partilham o endereço do proxy, e uma pessoa a repetir uma palavra-passe errada pode impedir todos os outros de iniciar sessão durante algum tempo.

## Manter as portas privadas

Quando o proxy corre na mesma máquina, define `BIND_ADDRESS=127.0.0.1` no `.env` e corre `docker compose up -d`. As portas publicadas (a aplicação web, a API e, se os usares, o armazenamento e o Mailpit) passam a escutar só no localhost, e só são acessíveis através do proxy.
